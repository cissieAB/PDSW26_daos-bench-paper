\subsection{DAOS Architecture}

Lofstead et al. prototyped the initial DAOS design as a next-generation HPC I/O stack by replacing POSIX file and directory abstractions with a distributed, object-based model featuring containers, versioned objects, and epoch-based consistency mechanisms \cite{daos-exascale-storage2016sc}.
Liang et al. then presented a full description of the DAOS system built on top of persistent memory (PMem) and NVMe SSDs \cite{daos-intro2020}. Hennecke et al. adapted the architecture to replace PMem with DRAM, demonstrating that DRAM maintains competitive performance \cite{daos-dram-intro2023}. 

Fig.~\ref{fig:daos-arch} shows the DAOS architecture, which consists of client/compute nodes and server/storage nodes. The \texttt{libdaos} library is the fundamental client-side software component. \texttt{libdfs} implements the POSIX abstractions over \texttt{libdaos}. An interception library \texttt{libpil4dfs} bridges POSIX applications and \texttt{libdfs}, providing kernel bypass for both data and metadata operations, while its predecessor \texttt{libioil} offers a narrower interception covering data I/O only. \textit{dfuse} exposes DAOS as a POSIX filesystem via the Linux FUSE (filesystem in userspace) layer. The DAOS storage engines on the server node manage two storage tiers: DRAM/PMem and NVMe SSDs. The RDMA-based data path between DAOS clients and servers traverses high-speed fabrics, such as HPE Slingshot or InfiniBand.

DAOS organizes storage into three hierarchical abstractions: pools, containers, and objects.
A pool is a storage reservation spanning one or more storage engines and is the only abstraction tied to physical capacity. Within a pool, a container serves as a logical namespace that can hold an arbitrary number of objects. DAOS containers support multiple access interfaces, including POSIX, HDF5~\cite{hdf5-daos2022tpds}, Python (via \texttt{pydaos}), etc., each corresponding to a container type.
When creating containers, users configure properties such as the container type, redundancy factor, and erasure coding cell size. 



\subsection{DAOS Performance Analysis}

\textit{fio} (Flexible I/O Tester)~\cite{fio-github} and IOR~\cite{ior-github, ior-paper2008sc} are two widely used I/O benchmarking tools.
\textit{fio} targets single-node performance and supports a broad range of I/O engines and sequential and random access patterns.
IOR is an MPI-based benchmark suite. Its \texttt{ior} executable measures aggregate bulk I/O throughput across MPI ranks, while \texttt{mdtest} measures metadata operations such as file creation and removal.
IO500~\cite{io500-announce2017, io500-github} defines representative workloads (e.g., ior-easy/hard, mdtest-easy/hard) built on top of IOR to produce a composite ranking score that serves as a standard reference for comparing large-scale HPC storage systems.


Both tools have been widely adopted in prior DAOS performance studies.
