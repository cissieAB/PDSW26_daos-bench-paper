\subsection{DAOS Architecture}

Lofstead et al. prototyped the initial DAOS design as a next-generation HPC I/O stack by replacing POSIX file and directory abstractions with a distributed, object-based model featuring containers, versioned objects, and epoch-based consistency mechanisms \cite{daos-exascale-storage2016sc}.
Liang et al. then presented a full description of the DAOS system built on top of persistent memory (PMem) and NVMe SSDs \cite{daos-intro2020}. Hennecke et al. adapted the architecture to replace PMem with DRAM, demonstrating that DRAM maintains competitive performance \cite{daos-dram-intro2023}. 

Fig.~\ref{fig:daos-arch} shows the DAOS architecture, which consists of client/compute nodes and server/storage nodes. The \textit{libdaos} library is the fundamental client-side software component. \textit{libdfs} implements the POSIX abstractions over \textit{libdaos}. An interception library \textit{libpil4dfs} bridges POSIX applications and \textit{libdfs}, providing kernel bypass for faster I/O, while \textit{dfuse} enables POSIX filesystem access via the Linux FUSE (filesystem in userspace) interface. The DAOS storage engines on the server node manage two storage tiers: DRAM/PMem and NVMe SSDs. The RDMA-based data path between clients and servers traverses high-speed fabrics, such as HPE Slingshot or InfiniBand.

DAOS organizes storage into three hierarchical abstractions: pools, containers, and objects.
A pool is a storage reservation spanning one or more storage engines and is the only abstraction tied to physical capacity. Within a pool, a container serves as a logical namespace capable of holding billions of objects. DAOS containers support multiple access interfaces, including POSIX I/O, HDF5~\cite{hdf5-daos2022tpds}, Python (via \textit{pydaos}), etc., each corresponding to a container type.
When creating containers, users configure properties such as the container type, redundancy factor, and erasure coding cell size.

\textit{fio} (Flexible I/O tester)~\cite{fio-github} and IOR~\cite{ior-github, ior-paper2008sc} are widely used benchmarking tools for measuring storage throughput, latency, and IOPS.
\textit{fio} targets single-node performance and supports a broad range of I/O engines and sequential and random access patterns.
IOR is an MPI-based HPC benchmark suite. Its \texttt{ior} executable measures aggregate bulk I/O throughput across MPI ranks, while \texttt{mdtest} measures metadata operations such as file creation and removal.
IO500~\cite{io500-announce2017, io500-github} defines representive workloads (\textit{ior-easy}, \textit{ior-hard}, \textit{mdtest-easy}, \textit{mdtest-hard}) built on top of these two tools to produce a composite ranking score, serving as a standard reference for comparing large-scale HPC storage systems.
