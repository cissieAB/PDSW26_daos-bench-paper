\subsubsection{Aurora}
Aurora is Argonne National Laboratory's exascale supercomputer with over 10,000 compute nodes \cite{aurora-intro2025}. Aurora currently has the largest DAOS deployment in production, comprising 1,024 storage nodes \cite{aurora-daos-slingshot-rpc2025cug, io500-ics26}. We were allocated a 100~TB DAOS pool under the \texttt{daos\_user} group. Per the Aurora user guide \cite{daos-aurora-guide} and our system queries, this group spans 128\footnote{Only 126--127 nodes were active during the experiments. } storage nodes, each with sixteen PMem devices and two 200Gbps Slingshot-11 Ethernet NICs.

{\color{blue}
The Aurora supercomputer nodes are interconnected via a large-scale Dragonfly network \cite{aurora-intro2025, daos-aurora-guide}. The 1,024 DAOS server nodes in 64 racks are organized into 8 Dragonfly groups, while compute/client nodes are distributed across 166 Dragonfly groups. This topology enables efficient communication between arbitrary client-server pairs, yet still incurs non-negligible latency due to multi-hop routing. This explains why the bandwidth numbers measured in our experiments are lower than those reported in \cite{DAOS-aurora-20-node-test2024scw}, which is based on the same node specifications but a much simpler network topology.

\subsection{DAOS Benchmark Configurations}

\subsubsection{I/O concurrency}

In a scientific streaming system such as E2SAR \cite{e2sar-github}, multiple data streams are produced and consumed simultaneously across a network of nodes, placing high concurrent I/O demand on the storage backend. We study two dimensions of this concurrency: intra-node concurrency, where a single client node issues multiple parallel I/O requests using \textit{fio}; and inter-node horizontal scaling, where multiple client nodes access DAOS simultaneously, evaluated with IOR.

The \textit{fio} job concurrency is controlled by two parameters: the number of jobs (denoted $nj$), where each job is an independent worker thread that issues I/O requests, and the I/O queue depth (denoted $iod$), which specifies how many I/O requests each job can have in flight simultaneously. Their product $nj \times iod$ therefore determines the overall concurrency level. In addition, the \textit{fio} parameter block size (denoted $bs$) significantly influences throughput/latency. We systematically vary these parameters across three experiment designs:

\begin{enumerate}[label=(\alph*)]
    \item Single-job, sweep $bs$ and $iod$. The tested block sizes are 4~KiB, 16~KiB, 1~MiB, 2~MiB, and 4~MiB, corresponding to the NVMe sector size, {\color{blue} a typical sub-chunk I/O unit}, the DAOS POSIX container chunk size, the huge page size, and bulk transfers, respectively.
    \item Fix $iod$, sweep $nj$ and $bs$. This isolates the combined effect of job-level parallelism and block size.
    \item Fix total concurrency ($nj \times iod$) and  $bs$, sweep the $nj/iod$ split. This quantifies how concurrency structure affects tail latency at similar throughput.
\end{enumerate}



\subsubsection{Workload read/write pattern}

In traditional filesystems, sequential access significantly outperforms random. DAOS, in contrast, narrows this gap through its log-structured storage engine and byte-addressable object store. 

To investigate this effect, we test \textit{fio} under five read/write mixes: (1) read-only; (2) read-heavy (20\% write); (3) read-balanced (50\% write); (4) write-heavy (80\% write); and (5) write-only, each mix with both random and sequential access. We use the \texttt{dfs} I/O engine with block sizes ranging from 4~KiB to 4~MiB. This configuration enables a systematic comparison of DAOS sequential versus random I/O performance. 

The five mixes also mirror the distinct stages of a scientific streaming workflow: write-only and write-heavy configurations correspond to data ingestion phases where detectors or simulations produce data at a high rate; balanced and read-heavy configurations represent concurrent online analysis, where processed and raw data coexist; and read-only configurations reflect post-processing or visualization stages that consume previously stored data.


\subsubsection{DAOS POSIX container access approaches}

Mounting a DAOS POSIX container via \textit{dfuse} provides the most portable approach, allowing unmodified POSIX applications to access DAOS through standard filesystem interfaces, but incurs overhead on every operation. To demonstrate the performance degrade, we evaluate \textit{fio} and IOR with three POSIX container access approaches on Sys-A:

\begin{enumerate}[label=(\alph*)]

\item \textbf{dfuse}: Mount the DAOS POSIX container via \textit{dfuse} and access it through \textit{fio}/IOR's POSIX engine.

\item \textbf{dfuse + IL}: Same as (a), but with DAOS interception library (IL) \texttt{libioil} or \texttt{libpil4dfs} preloaded.

\item \textbf{dfs}: Use \textit{fio} or IOR's native \texttt{dfs} engine, bypassing \textit{dfuse} and POSIX filesystem entirely.

\end{enumerate}

\subsection{DAOS vs.\ Other Storage Systems}

Both NVMe over Fabrics (NVMe-oF) and DAOS target high-bandwidth access to remote NVMe media over high-speed fabrics, making a direct comparison instructive. The client node of Sys-B has a read-only NVMe-oF volume mounted over a 100~Gbps RDMA Ethernet link. We copy a 28~GiB file from the NVMe-oF volume to a DAOS POSIX container and measure sequential read throughput with \textit{fio}. To avoid confounding the comparison with the peak-bandwidth difference between the 100~Gbps Ethernet and 200~Gbps InfiniBand fabrics, we restrict the test to a single job with block sizes ranging from 4~KiB to 4~MiB, keeping achieved throughput well below the theoretical peak of either fabric.
