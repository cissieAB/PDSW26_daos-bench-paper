\subsection{Benchmark Methodology}

Unless otherwise stated, we use the \texttt{dfs} engine for both IOR and \textit{fio}, which bypasses the Linux kernel I/O stack, including the page cache. Each configuration is repeated at least 10 times, and we report median values. We use the coefficient of variation, defined as the standard deviation divided by the mean, to quantify measurement variability.

We use \textit{fio} to characterize I/O performance within a single client node and IOR to evaluate throughput across multiple client nodes. In \textit{fio}, the number of jobs ($nj$) specifies the number of parallel processes, while the I/O queue depth ($iod$) specifies the number of I/O requests each process can have in flight. For asynchronous engines such as \texttt{dfs}, $nj\times iod$ determines the total I/O concurrency. Synchronous engines such as \texttt{pvsync2} issue one blocking request at a time regardless of $iod$. We denote the I/O request size as $rs$, corresponding to \textit{fio}'s \texttt{bs} parameter and IOR's transfer size (\texttt{-t}). For multi-node IOR experiments, PPN denotes the number of MPI processes per node.

Across the \textit{fio} experiments, we consider request sizes of 4~KiB, 16~KiB, 1~MiB, 2~MiB, and 4~MiB. We vary I/O request size, I/O concurrency, client-node count, read/write mix, sequential and random access, and object size and count. We also compare three methods for accessing DAOS POSIX containers: plain POSIX access through \textit{dfuse}, the DAOS interception library (IL), and the native DFS interface. Finally, we use NFS as a conventional network file system reference for comparison with DAOS.

\subsubsection{I/O Concurrency}

In a scientific streaming system, multiple data streams are produced and consumed simultaneously, imposing high concurrent I/O demands. We study the intra-node concurrency with \textit{fio}, where a single client node issues multiple parallel I/O requests, and node-level scaling with IOR, where multiple client nodes work simultaneously.

The \textit{fio} task concurrency is controlled by two parameters: the number of jobs (denoted $nj$), where each job runs as a separate process that issues I/O requests, and the I/O queue depth (denoted $iod$), which specifies how many I/O requests each process can have in flight simultaneously. For asynchronous I/O engines such as \texttt{dfs}, the product $nj \times iod$ determines the overall concurrency level. Synchronous engines, such as \texttt{pvsync2}, issue one blocking request at a time, regardless of $iod$. In addition, the granularity of each I/O request (\textit{fio}'s \texttt{bs} flag, denoted $rs$ to unify with IOR's transfer size \texttt{-t}) substantially influences both throughput and latency. We systematically vary these parameters across three experiment designs:

\begin{enumerate}[label=(\alph*)]
    \item Single-process, sweep $rs$ and $iod$. The tested request sizes are 4~KiB, 16~KiB, 1~MiB, 2~MiB, and 4~MiB, corresponding to the CPU page size, the modern GPU page size, the DAOS POSIX container's default chunk size, the huge page size, and bulk transfers, respectively.
    \item Fix $iod$, sweep $nj$ and $rs$. This characterizes process-level parallelism across I/O request sizes.
    \item Fix total concurrency ($nj \times iod$) and $rs$, sweep the $nj/iod$ split. This quantifies how concurrency structure affects tail latency at similar throughput.
\end{enumerate}

For inter-node scalability, we run MPI \texttt{ior} processes across up to 128 DAOS client nodes, with each process issuing sequential I/O requests of a fixed $rs$. We sweep the number of nodes and MPI processes per node (PPN), reporting aggregated read and write bandwidth. These results reveal the throughput limit for scientific streaming pipelines at scale.



\subsubsection{DAOS POSIX Container Access Approaches}

Mounting a DAOS POSIX container via \textit{dfuse} is the most portable approach, allowing unmodified POSIX applications to access DAOS through standard Linux filesystem interfaces, at the cost of lower throughput. To quantify this overhead, we evaluate IOR with three POSIX container access approaches on Sys-A: (a) POSIX: Mount the DAOS POSIX container via \textit{dfuse} and access it through the IOR POSIX module; (b) IL: Same as (a), but with the DAOS interception library (IL) \texttt{libpil4dfs} preloaded; and (c) DFS: Use IOR \texttt{dfs} module, bypassing \textit{dfuse} entirely.



\subsubsection{Access Patterns}

In traditional filesystems, sequential access significantly outperforms random access. DAOS narrows this gap through its log-structured storage engine and byte-addressable object store. To investigate this effect, we benchmark \textit{fio} across five read/write mixes, where read and write I/O requests are issued simultaneously: (1) read-only; (2) read-heavy (20\% write); (3) balanced (50\% write); (4) write-heavy (80\% write); and (5) write-only, each tested under both random and sequential access. These five mixes also mirror the distinct stages of a scientific streaming workflow: write-only and write-heavy configurations correspond to data ingestion, where detectors or simulations produce data at high rates; balanced and read-heavy configurations represent concurrent online analysis, where processed and raw data coexist; and read-only configurations reflect post-processing or visualization stages.


In addition, we evaluate how object/file size and count affect read throughput at scale. On Sys-A, we create two 1~TiB DAOS containers: one holds 64 16~GiB objects, and the other holds many 4~MiB objects. We use MPI-launched \textit{fio} processes to read from both containers and compare the throughput. This informs the storage design for detector-generated events in scientific streaming pipelines, where individual events are small but must be retrieved at sustained high rates.



\subsection{DAOS vs.\ Other Storage Systems}


The client node of Sys-B also has access to an NVMe-based storage node via the Network File System (NFS, v4.2) over TCP/IP on a 100~Gbps ConnectX-6 Dx Ethernet fabric. Comparing DAOS to this NFS quantifies the performance gap between a conventional file-sharing stack and a modern object store with native RDMA transport. To avoid confounding the comparison with the peak-bandwidth difference between the 100~Gbps Ethernet and 200~Gbps InfiniBand fabrics, we restrict the test to a single process, keeping throughput well below the theoretical peak of either fabric.
