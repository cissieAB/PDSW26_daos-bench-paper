\subsection{Streaming Throughput}
\label{sec:rq1_throughput}

Scientific streaming imposes high concurrent I/O demands and requires throughput to scale across client nodes. We characterize how I/O request size, concurrency, DAOS access method, and client count affect read and write throughput.

\subsubsection{I/O Concurrency}

Fig.~\ref{fig:fio-sweep-bs_iod} shows the single-process results as $iod$ varies. The coefficient of variation remains below 8\% across all configurations. I/O request size has a greater impact on throughput than queue depth. The two small request sizes (4~KiB and 16~KiB) yield consistently low bandwidth of 0.38--0.70~GiB/s and 1.19--2.30~GiB/s, respectively, and saturate at $iod{\geq}32$. In contrast, the 1, 2, and 4~MiB requests increase sharply from $iod{=}4$ to $iod{=}8$ and plateau at 16--21~GiB/s for $iod{\geq}16$, roughly an order of magnitude above the small-request regime. At $iod{=}64$, the median IOPS is 176~K for $rs{=}4$~KiB and 18~K for $rs{=}1$~MiB, so the 4~KiB configuration sustains nearly 10$\times$ the request rate while delivering 26$\times$ lower throughput. CPU utilization remains near 100\% for $rs{=}$4/16~KiB across all queue depths, indicating that small-request performance is CPU-bound.

We next fix $iod{=}16$ and vary the number of \textit{fio} jobs, as shown in Fig.~\ref{fig:fio-sweep-bs_nj}. Multiple jobs write to one large DAOS object, and throughput has a coefficient of variation below 11\% across all configurations. The 1/2/4~MiB requests are already near peak throughput at $nj{=}4$, reaching 22.5--22.7~GiB/s, over 95\% of the client NIC limit. Their throughput remains nearly flat as $nj$ increases, with a slight decrease to 21.2--21.5~GiB/s at $nj{\geq}32$, indicating that additional process concurrency provides little benefit once the client NIC is saturated. In contrast, the two small request sizes continue to benefit from additional processes and saturate at $nj{\geq}16$, reaching 6.9~GiB/s and 16.7~GiB/s for 4~KiB and 16~KiB, respectively, approximately 7$\times$ higher than their single-process throughput.

The two results consistently show that I/O request size has a larger impact on throughput than either queue depth or process count. The DAOS chunk size is the largest I/O size that a client sends to a storage target in a single request~\cite{daos-user-guide}. On Sys-B, the chunk size is 1~MiB. Therefore, 2/4~MiB \textit{fio} operations are divided into multiple 1~MiB DAOS requests, whereas 4/16~KiB operations issue much smaller requests and require substantially higher request rates to utilize the available bandwidth. As a result, MiB-scale requests reach the client NIC limit with modest concurrency, while small requests require both deeper queues and additional processes to improve throughput.

\begin{takeaway}
\textbf{Takeaway:} I/O request size dominates DAOS throughput. MiB-scale requests reach the client NIC bandwidth with modest concurrency, while small requests remain CPU- and IOPS-bound and require higher queue and process concurrency to improve throughput.
\end{takeaway}

\subsubsection{DAOS Client Access Methods}

We next compare three DAOS client access methods on Sys-A using the IOR read-after-write workload with PPN\,=\,48 and $rs{=}2$~MiB: plain POSIX access through \textit{dfuse}, the interception library (IL), and the native DFS interface. The Linux page cache is disabled for all three methods. Plain POSIX access achieves 3.26~GiB/s for reads and 0.75--0.81~GiB/s across write iterations, while DFS achieves 74~GiB/s for reads and 107--131~GiB/s across write iterations, corresponding to 23$\times$ and up to 130$\times$ higher throughput, respectively. Since DFS and IL achieve much higher throughput than plain POSIX access, Fig.~\ref{fig:access-cmp} compares their per-iteration behavior in more detail.

Plain POSIX access achieves 3.26~GiB/s for reads and 0.75--0.81~GiB/s for writes, while DFS achieves 74~GiB/s for reads and 107--131~GiB/s for writes, corresponding to 23$\times$ and up to 130$\times$ higher throughput, respectively. Fig.~\ref{fig:access-cmp} compares DFS and IL at the per-iteration level to examine their performance difference.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=1\linewidth]{figures/ior_rw_time-nocache.pdf}
\caption{Per-iteration IOR wall time for DFS and IL, decomposed into data-transfer and non-transfer time (PPN\,=\,48, $rs{=}2$~MiB). Error bars show the min--max range across runs.}   \label{fig:access-cmp}
\end{figure}


IL achieves throughput comparable to DFS but shows substantially higher variability during writes. In particular, the first write iteration is consistently slower than subsequent iterations, which we refer to as write-cold and write-warm, respectively. Fig.~\ref{fig:access-cmp} decomposes the per-iteration wall time into data-transfer time and the remaining non-transfer time. We obtain the data-transfer time from the per-operation latency reported by IOR and the number of I/O operations, and compute the non-transfer time as the difference between the total iteration wall time and the data-transfer time. Thus, the non-transfer component represents residual time not accounted for by data transfer and may include metadata processing, synchronization, and other runtime overhead. The non-transfer component is negligible for reads and write-warm iterations for both methods. For write-cold, however, the non-transfer time is 22\% of the DFS transfer time, while for IL it is 2.5$\times$ the transfer time. Considering data transfer alone, IL reads are 11\% faster than DFS reads, while IL writes are 2--9\% slower.

These results show that both DFS and IL avoid the large overhead of plain \textit{dfuse} access. Their estimated data-transfer times are comparable, but IL has a much larger non-transfer component during the cold write, resulting in less consistent write performance.

\begin{takeaway}
\textbf{Takeaway:} Plain POSIX access through \textit{dfuse} incurs substantial throughput overhead. Both DFS and the interception library provide much higher throughput, but IL incurs a large non-transfer cost during the cold write and therefore shows less consistent write performance than DFS.
\end{takeaway}

\subsubsection{Client-Node Scaling}
%\subsubsection{Multi-Node Scaling}
\label{sec:multinode}

We further evaluate throughput scaling across DAOS client nodes on Sys-A using IOR read-after-write workloads. To characterize the upper throughput limit, we set the DAOS POSIX container redundancy factor (\texttt{rd\_fac}) to 0 instead of its default value of 3. Following~\cite{DAOS-aurora-20-node-test2024scw}, we bind MPI processes to CPU cores using the breadth-skip method. We evaluate PPN\,=\,8, 16, 32, and 48 with $rs{=}2$ and 16~MiB, while the \texttt{dfs} chunk size is 2~MiB. Throughput has a coefficient of variation below 11\% for all configrations. Fig.~\ref{fig:ior-scaling} shows client-node scaling at PPN\,=\,48 (left) and PPN scaling at $n{=}128$ client nodes (right).

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=1\linewidth]{figures/ior-scaling.pdf}
    \caption{IOR median read-after-write bandwidth: client-node scaling with 48 MPI processes per node (PPN\,=\,48) (left) and PPN scaling at $n{=}128$ client nodes (right).}
    \label{fig:ior-scaling}
\end{figure}

As shown in the left panel, DAOS throughput scales near-linearly with the number of client nodes before saturation, and the 16~MiB request size consistently outperforms the 2~MiB request size. For $rs{=}16$~MiB, median write and read bandwidths increase from 169.2 and 108.7~GiB/s at one client node to 1971.1 and 1824.5~GiB/s at 16 client nodes, and further to 5371.6 and 5507.1~GiB/s at 128 client nodes. The aggregate NIC bandwidth of the 126 active DAOS storage nodes is 5867.3~GiB/s, and the measured throughput at 128 client nodes exceeds 90\% of this value, indicating that throughput is limited by the storage-side network at this scale.

The right panel shows that larger I/O requests require less process concurrency to approach peak throughput. For $rs{=}16$~MiB, PPN\,=\,8 already achieves more than 80\% of the PPN\,=\,48 bandwidth, and throughput is nearly flat beyond PPN\,=\,32. In contrast, the 2~MiB workload continues to benefit from increasing PPN, with read throughput increasing by 3.5$\times$ from PPN\,=\,8 to 48. Read throughput eventually exceeds write throughput, but only at high process counts: the crossover occurs at 1024 MPI processes for $rs{=}16$~MiB and at 6144 MPI processes for $rs{=}2$~MiB.

\begin{takeaway}
\textbf{Takeaway:} DAOS scales to multi-TiB/s with tens of client nodes on Sys-A, and larger I/O request sizes saturate at lower process concurrency. Write throughput exceeds read throughput at moderate process counts, while the crossover occurs only at very high concurrency.
\end{takeaway}

\subsection{Concurrency and Tail Latency}
\label{sec:rq2_latency}

High throughput alone is insufficient for scientific streaming, where an individual slow write can introduce backpressure into the pipeline. We therefore examine whether tail latency depends only on the total I/O concurrency or also on how that concurrency is distributed between processes and per-process queues. On Sys-B, we evaluate five $nj/iod$ configurations with $nj\times iod$ fixed at 256 and $rs{=}1$~MiB, with each \textit{fio} process writing to a separate object. Across all configurations, the mean latency remains nearly unchanged at 10.8--11.1~ms, while throughput remains comparable. Fig.~\ref{fig:fio-tail-latency-breakdown} shows how the latency distribution changes despite the same total concurrency.

%\subsubsection{Tail Latency at Fixed Concurrency}

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=1\linewidth]{figures/fio-tail_latency_breakdown.pdf}
    \caption{Latency breakdown of \textit{fio} \texttt{randwrite} at fixed total I/O concurrency ($nj\times iod{=}256$, $rs{=}1$~MiB).}
    \label{fig:fio-tail-latency-breakdown}
\end{figure}

%We evaluate five $nj/iod$ combinations on Sys-B with their product fixed at 256 and $rs$=1~MiB. Every \textit{fio} process writes to an individual object. Across all configurations, the mean latency (10.8--11.1~ms) remains consistent, while maximum latency varies from 144 to 165~ms. 

\textit{fio} separates I/O latency into submission latency ($slat$) and completion latency ($clat$). Mean $slat$ remains negligible at 0.03--0.06~ms across all configurations, and completion latency dominates the overall I/O latency. As shown in Fig.~\ref{fig:fio-tail-latency-breakdown}, the P50 $clat$ changes only moderately across configurations, whereas P99.99 is highly sensitive to the process/queue-depth configuration. With $nj{=}4$ and $iod{=}64$, P99.99 $clat$ reaches 143.7~ms, approximately 26$\times$ the P50. Increasing the process count while reducing the per-process queue depth lowers P99.99 $clat$ to approximately 75~ms, despite the fixed total concurrency and comparable throughput.

Shallower queues, however, increase worst-case submission latency. At $iod{=}8$ and 4, the maximum $slat$ reaches 45.6 and 67.9~ms, respectively, more than 1000$\times$ the mean $slat$. These results reveal a tradeoff within the same total concurrency: deeper per-process queues increase completion tail latency, whereas very shallow queues can incur large submission-latency spikes. For latency-sensitive streaming, using more processes with a shallow-to-moderate queue depth provides a better balance.

\begin{takeaway}
%\textbf{Takeaway:} At fixed total concurrency, tail latency is highly sensitive to the $nj/iod$ split. More processes with shallower per-process queues reduce tail latency at the cost of higher submission overhead.
\textbf{Takeaway:} Total I/O concurrency alone does not determine tail latency. At the same $nj\times iod$, using more processes with shallower queues substantially reduces P99.99 completion latency while maintaining comparable throughput, although very shallow queues increase worst-case submission latency.
\end{takeaway}









\subsection{Data Access Performance}
\label{sec:rq3_us}

Scientific streaming workflows span write-dominated data production, mixed read/write analysis, and read-dominated post-processing. We next examine how request size and access order affect these read/write patterns, and how storing data as many small objects affects later read performance.

\subsubsection{Read/Write Patterns}

We first evaluate five read/write mixes on Sys-B using \textit{fio} with $nj{=}iod{=}16$: read-only, read-heavy (20\% write), balanced (50\% write), write-heavy (80\% write), and write-only. Each mix is tested under both random and sequential access with $rs{=}$4~KiB, 16~KiB, 1~MiB, 2~MiB, and 4~MiB. Fig.~\ref{fig:fio-all-pattern} shows the 10-run median throughput. Write throughput substantially exceeds read throughput. For $rs{\geq}1$~MiB, write-only throughput saturates at 22.4--22.9~GiB/s, whereas read-only throughput plateaus near 4.6~GiB/s, making write-only throughput approximately five times the read-only throughput. Consequently, aggregate throughput increases monotonically with the write fraction across the five read/write mixes.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=1\linewidth]{figures/fio-bw-all-pattern-nj16-iod16.pdf}
    \caption{Throughput for different \textit{fio} read/write mixes.}
    \label{fig:fio-all-pattern}
\end{figure}

The effect of access order depends strongly on I/O request size. When $rs{\geq}2$~MiB, sequential and random throughput differ by less than 7\% for all read/write mixes, indicating that coarse-grained I/O is largely insensitive to access order. At smaller request sizes, however, access order has a substantial effect. At $rs{=}4$~KiB, read-related throughput under sequential access is 2--6$\times$ higher than under random access, while sequential write-only throughput is only 53\% of random write throughput. At $rs{=}16$~KiB, random and sequential write-only throughput differ by 73\%, while the other read/write mixes remain within 18\%. Thus, small I/O requests are sensitive to access order, with sequential access favoring reads and random access favoring writes.

At $rs{=}4$~KiB, sequential reads show an initial warm-up effect, with the first two runs 33\% and 17\% below steady state. At $rs{\geq}1$~MiB, the low-throughput outliers instead occur episodically. We leave the underlying cause of this variability for future investigation.

This shows that the number of objects per rank, not the total data volume per rank, drives the small-object read penalty. This per-object overhead compounds as node count grows, causing small-object throughput to plateau.


The large-object configuration, with one 16~GiB object per rank, scales nearly linearly with client-node count, from 73~GiB/s at 2 nodes to 457~GiB/s at 16 nodes. In contrast, the small-object configurations scale much more slowly. With 4096 4~MiB objects per rank, which matches the 16~GiB data volume per rank of the large-object configuration, throughput reaches only 89~GiB/s at 8 nodes and 91~GiB/s at 16 nodes, 3--5$\times$ lower than the large-object configuration. Small-object throughput also changes with the number of objects per rank: although 1024 objects per rank reaches 107~GiB/s at 2 nodes, its throughput grows much more slowly than the large-object configuration as the client count increases.

The matched-volume comparison shows that storing the same amount of data as many small objects introduces substantial read overhead. As the number of client nodes increases, this per-object overhead limits small-object scaling and causes throughput to plateau. For scientific streaming systems that produce many small events, aggregating events into fewer, larger DAOS objects can therefore substantially improve later read performance.



\begin{takeaway}
\textbf{Takeaway:} Reading many small objects achieves substantially lower throughput than reading large objects at the same data volume, and the gap increases with client-node scale. Aggregating small events into fewer, larger objects can therefore improve read performance.
\end{takeaway}


\subsubsection{DAOS vs.\ NFS}

We compare DAOS with NFS to provide a conventional file-system reference for the effect of I/O request size. The Sys-B client accesses DAOS over its 200~Gbps InfiniBand network and an NVMe-based NFS v4.2 storage node over a 100~Gbps Ethernet network. To reduce the influence of this peak-bandwidth difference, we use a single \textit{fio} process so that the measured throughput remains below the network capacity of either system. We copy the same 28~GiB file to an NFS-mounted volume and a DAOS POSIX container and measure sequential-read throughput. DAOS uses the \texttt{dfs} engine with $iod{=}32$, while NFS uses the \texttt{pvsync2} engine, which provides the highest NFS throughput among the tested \textit{fio} engines. Each run reads the file exactly once. The Linux page cache is enabled for the NFS path, while the DAOS \texttt{dfs} path bypasses it. NFS throughput changes only moderately with I/O request size, increasing from 0.62~GiB/s at 4~KiB to 0.83~GiB/s at 4~MiB, while CPU utilization increases from 59.7\% to 69.3\%.
